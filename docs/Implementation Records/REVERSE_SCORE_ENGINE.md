# Reverse Score Engine (v1)

New product surface (separate from the optimizer): given the observables a
RoBeats leaderboard row exposes for one play — **score**, **naked/casual
score**, **accuracy**, **gear power** — recover the equivalence class of
loadouts consistent with them. Lives entirely under `reverse_score/`
(own tests in `reverse_score/tests/`); imports from `gear_optimizer` only
where reuse saves real code. Endpoint: `python -m reverse_score`.

## Observable semantics (decompiled ground truth, [REDACTED PRIVATE REPOSITORY])

| Observable | Definition | Source |
|---|---|---|
| Score | geared score; per hit `floor((points + colorBonus) × chainMult × feverMult)` | `PlayerScore.lua:228` |
| Naked score | parallel score object with the all-zero statsdict — gear-independent | `ScoreManager.lua`, `ServerGameInstance_GameEnded.lua:108` |
| Gear multiplier | `score / naked_score` server-side; **redundant** given both scores | `ServerLeaderboardDatastoreManager.lua:428` |
| Gear power | `5×Σ(raw PP,CM,FF,FM,FT) + 6×c₁` (1-color) or `+4×c₁+2×c₂` (2-color); raw (unclamped) totals | `PlayerBlobAvatar.lua:650`, submitted base+color at `GameEnded.lua:73` |
| Accuracy | `(P + 0.75G + 0.25O) / hitCount`; 5 dp in the API payload | `PlayerScore.lua:311` |

Hardwired live-game constants (no flags): `ExtendedGearStatCap160=true`
(effective clamp −80..160), `PetRankUpEnabled=true` (pet color scaling uses
floor), `ColorGearStatsEnabled=true` (upgrade tables use the color branch).
The game's "day/week modifier" statsdict is the team-buff expiry gate only
(`PlayerBlobAvatar.lua:102-112`) — modeled as the team-buff loadout variable.

## Architecture

- `game_model.py` — 1:1 ports: `BezierDist` (arc-length cubic bezier, 10
  segments), the `f_N` 5-anchor stat curve and every stat curve on it, gear
  power, per-hit color bonus weights, the PetUtils mini scaling law
  (rank× base mods; colors × `floor(lerp 1→5 over level 1→50)`; rank caps
  level 20/30/40/50).
- `webport_extract.py` — strict parsers for decompiled PetInfo files (90
  pets: base/color statmodifierobjs + rarity) and `EquipmentUpgradesSet1`
  (22 upgrade types, including negative-stat variants such as
  PerfectTime+ = +1 PT / −1 PP). Per-piece upgrade capacity: 15
  (`EquipmentUpgradeDatabase.upgrade_count_can_upgrade`).
- `domain.py` — loadout model (6 gear slots, per-piece upgrades, ≤3 minis
  with level/rank/ascension, gems, team buff) and statsdict composition.
  Reuses optimizer gem scales, `team_buff_effect`, and the canonical
  `mini_ascension` materialization. **Minis.csv rows are the level-1/rank-1
  base values** (verified identical to PetInfo for USAO/t+pazolite/
  Electroman); every intermediate level/rank is generated by the scaling law.
- `oracle.py` — forward map via the **canonical exact scorer**
  (`score_stats_exact[_batch]`); no scoring duplication. Song context =
  `get_base_calc_song` → clone → `apply_timing_envelope(perfect_window)` →
  timeline frontier payload. v1 is all-Perfect (accuracy == 1) semantics.
- `synthetic.py` — seeded generator sampling strictly inside a `DomainSpec`
  (same spec the engine enumerates ⇒ closed round-trips).
- `engine.py` — the sieve: meet-in-the-middle candidate generation
  (pre-fold three small groups — virtuals, gear slots 1-3, gear slots 4-6 —
  then join under the exact-P suffix window, largest group last), chunked
  int32 expansion bounded by `_EXPAND_BUDGET_ROWS` (~112 MB/step), retained
  rows capped by `max_rows` (loud `EngineError`, never silent truncation),
  exact-S filter through the oracle, witness DFS with per-suffix bounds, and
  an always-on **soundness gate** (every witness re-scored; any mismatch
  raises).

## Invariants and guarantees

- **Soundness**: machine-checked per query — every returned loadout
  reproduces (S, N, P) exactly or the engine raises.
- **Completeness**: exhaustive within the `DomainSpec`; domain gaps surface
  as empty results or `DomainMismatch` (naked-score check = wrong chart /
  version drift), never fuzzy matches.
- **Uniqueness**: the answer is an equivalence class. Perfect Time (and any
  off-song-color stat) is invisible to all observables by construction;
  witnesses differing only there are one class.
- Net-negative visible stats (possible only by stacking negative upgrades on
  near-zero gear) are outside the canonical scorer's modeled domain
  (ref tables span 0..160) and fail loudly in `compose_stats`.

2. Gear power vs decompiled constants; pet scaling law endpoints + floors;

3. Synthetic round-trip on a real chart (LOVERS' OASIS Easy): generated

## Performance envelope (v1, measured)

- Scoring: ~0.04 ms/candidate through `score_stats_exact_batch` (CPU).
- Fold: mid-range P slices are genuinely fat (275k exact-P candidates even
  on a 6-items/slot test domain; ~12 s fold + ~11 s scoring). Real top-tier
  rows sit in the thin upper P tail where slices collapse to 10²-10³.
- RAM: bounded by chunk budget + `max_rows` cap; verified with a
  low-available-RAM watchdog on the no-pagefile target box.

## Production layer (v1.5): speed + false-positive contract

- **Meet-in-the-middle with windowed group pre-folds**: gearL / gearR /
  minis (3 slot axes) / upgrades (pattern count axes) / gems A / gems B +
  buff pre-fold independently, each windowed against the other groups'
  P-complement range (two-pass); composites join smallest-first under the
  exact-P window. Windowed pre-folds are what make real per-type upgrade
  ceilings (15/piece) enumerable for tail-P (maxed) builds.
- **Monotone box pruning before scoring** -- with a measured correctness
  boundary: **Fever Time and Fever Fill Rate are NOT monotone in the exact
  score** (+1 FT measurably lowered S: longer fever repositions activation
  windows). They are frozen as bucket dims; the provably monotone free dims
  are exactly (colors, PP, CM, FM) at fixed (ft_idx, ff_idx). The
  pruned-vs-brute witness-set equivalence test is the standing guardian; it
  caught the original wrong-dim bucketing.
- **Parallel exact scoring**: persistent spawn pool, workers rebuild the
  song context from the disk timeline cache and stream chunks
  (``score_stats_batch_parallel``; picklable module-level workers).
- **False-positive contract**: (1) soundness gate re-scores every witness --
  zero unsound answers, machine-checked; (2) results are equivalence
  classes with K reported, never a point claim; (3) the naked score doubles
  as an FC-and-chart fingerprint for real rows (a rounded-up accuracy==1
  non-FC play fails the naked check loudly); (4) domain-cap misses return
  NO PREIMAGE with the cap named, never a nearest-fit guess.
- **Unmaxed AND maxed coverage**: production spec enumerates every pet at
  every rank-boundary level (knob: ``--mini-levels``), ascension 0/5/10 for
  targeted pets, per-type upgrades to the 15/piece game ceiling (knob:
  ``--upgrade-cap``), gems to ``--gem-cap``.
- **Non-FC layer 1 (judgment counts)**: ``judgments.feasible_judgment_counts``
  enumerates every (P,G,O,M) multiset consistent with the rounded accuracy
  via the deficit identity 4*(H - weighted) = g + 3o + 4m -- exact and
  complete. ``invert`` refuses accuracy<1 rows loudly (counts included in
  the error); ``invert-row`` prints the counts analysis for non-FC rows.
  Layer 2 (note-level sequence DP against the exact naked score) is the
  pending step before non-FC loadout inversion.

## Shipped contract (2026-07-17): recovery-correct + sound; class-completeness best-effort

Per user decision, the engine ships on two hard guarantees, with exact
equivalence-class completeness tracked as a non-blocking known-limitation:

- **SOUNDNESS (hard):** every returned witness re-scores to (S, N, P) exactly
  via the always-on forward gate in `invert()`. Zero false positives.
- **RECOVERY (hard, ship gate):** the true loadout is always in the returned
  class. Gate: `test_roundtrip_recovers_truth_and_witnesses_are_sound`,
  16-sample multi-seed (1337/777/11/42). Green.
- **CLASS COMPLETENESS (best-effort, tracked):** the FULL reported class of K
  equivalent loadouts matches enumerated-gem brute. Residual analytic-gem
  edge on a minority of samples; recovery + soundness unaffected. Tracked by
  `test_analytic_gem_class_completeness_known_gap` (xfail until closed, so it
  flips to a hard pass the moment fixed and never hides a regression).

Root cause fixed this session (the MISS that motivated the contract):
`_build_composites` windowed the non-gem groups to hit the FULL gear-power
target, ignoring that analytic gems supply most of P — so valid LOW-P non-gem
bases (e.g. the truth base at P=454 for a target of 567) were pruned before
the walk. Fix: `_GemModel.max_p()` feeds a `gem_slack` that widens the
non-gem windows and feasibility check on the low side. This also confirmed
the correctness/speed tension: correct enumeration of a heavily-geared row's
preimage is inherently large (millions of exact-P effective-states), which is
why real-row sub-10s needs the GPU + MITM architecture below, not CPU pruning.

## Primary identification path (2026-07-17): multi-row intersection

The adversarial design review (workflow wf_6d003e79-f4c) established that
sub-10s per maxed row is not reachable by reorganizing the search -- the
exact-P candidate volume is irreducibly millions -- and named multi-row
intersection the only lever that dodges that wall. Shipped as
`reverse_score/identify.py` + the `identify-player` CLI.

Mechanism: a player's loadout (gear, upgrades, minis, gems, buff) persists
across their songs while colors/charts/P-weights/scores vary. Invert ONE
tractable seed row to a candidate class, then FORWARD-FILTER that class
against each additional row (one exact score per candidate -- no fresh
search). Surviving all rows collapses the class toward K=1. Cost = one
inversion + O(class size) forward checks per extra row; no per-row sub-10s
needed. `canonical_form` is song-independent and `oracle.forward`
re-composes per song (mini ascension is song-specific in effect, persistent
in state), so the filter is exact across songs. Gate:
`test_multirow_intersection_collapses_class` -- truth always retained, class
shrinks vs single row, every survivor reproduces all rows (intersection
soundness). Seed selection prefers lowest gear power (fewer gem fillings ->
smaller seed class); rows that cap or fail the naked fingerprint are skipped
loudly, and a row that eliminates all survivors is reported (inconsistency),
never silently emptied.

## Speed roadmap (user-directed 2026-07-17): GPU scoring + MITM generator

(Adversarial-review caveats, must-fix before building -- see workflow
wf_6d003e79-f4c journal: GPU floor drift is a real RECOVERY risk, not just
speed -- the equality filter has no CPU net, so a 1-ULP mis-floor silently
drops a true preimage; needs an adversarial floor-boundary parity gate + ULP
CPU-recheck + i32-overflow guard. The MITM half-fold must carry a per-dim
committed-overflow scalar or it defeats clamp-dedup and blows up on the maxed
regime. These are speed refinements SECONDARY to multi-row intersection.)

Measured: constrained-domain lookups run min 3.65s / p50 11.5s / max 32s
single-core (worker pool -> sub-10s). Real maxed rows (P~5800) cap: the
exact-P effective-state set is millions. Sub-10s there requires:
1. **GPU exact scoring** on the 7900 XTX via the optimizer's Taichi/Vulkan
   eval path (bit-exact to the CPU reference scorer; repo GPU-first rule) --
   scores millions of candidate states at hardware throughput.
2. **Vectorized MITM generator** replacing the Python DFS walk: two-half
   hash-join on P-complement within the gem-slack band, then analytic gems.
Fallback / complement for identification: **multi-row intersection** (a
player's base loadout persists across their rows; the dump has 100+
rows/player) collapses the class toward K=1 without needing per-row sub-10s.
A design + adversarial-review pass produced the concrete plan; implementation
is serial, gate-guarded (recovery + soundness), RAM-watchdogged.

### 2026-07-17: first live confirmation of the coupled-timing signature

Three dump rows (Eggnog/Louder Now/Gateway, all Hard) miss the naked
fingerprint by exactly -800 each. USER-CONFIRMED CAUSE: press timing acts
on the NAKED fever bar, not the composite one -- the play's presses are
timed against the composite fever, and the naked score replays those
presses on the naked bar, landing below the naked all-Perfect ceiling.
This is precisely the failure signature the accuracy-contract section
below predicted for the independent-maxima assumption. Below-ceiling
mismatches are now classified distinctly from above-ceiling ones (wrong
chart / version drift) in both `invert()`'s DomainMismatch and the
invert-row fingerprint scan; inverting these rows requires the coupled
two-bar frontier (same DP family as the timeline frontier, doubled fever
state).

## Accuracy contract (user directive, 2026-07-16): model timing weirdness

Press timing within hit windows shifts fever activation ("the way you
press") and changes both the geared and naked scores for identical loadout +
judgments -- this repo has already proven it (perfect_window vs 0ms
envelopes score differently; the timeline frontier exists to enumerate
legal activation instants). The engine's oracle currently uses the
optimizer's ceiling-play semantics: geared and naked each modeled as an
INDEPENDENT maximum over legal timings. For "insanely accurate" results the
oracle must model the realizable **(geared, naked) pair under shared press
timing** -- the two bars fill at different rates from the same presses, so
their optima need not coincide.

Consequences and plan:
1. Timing-suboptimal or coupling-violating real plays today produce LOUD
   refusals (the naked fingerprint is timing-sensitive too), never wrong
   loadouts -- the failure mode is refusal, and its signature identifies
   this assumption.
2. Decisive measurement: the real-row fingerprint sweep. Systematic naked
   near-misses on true-FC rows = the independence assumption is wrong in
   practice; clean matches = ceiling plays realize both maxima.
3. If required: extend the timeline machinery to a coupled two-bar frontier
   (geared bar x naked bar over the shared press-timing envelope), yielding
   the achievable (S, N) pair set per loadout. Fingerprinting becomes pair
   membership; inversion's exact-S filter becomes pair-achievability. Same
   DP family as the existing frontier, doubled fever state.
4. The non-FC sequence layer inherits the same envelope treatment (held-tail
   carry clocks and early/whiff releases included -- both already modeled in
   the optimizer's timing envelopes).

## 2026-07-17 (session 2): vectorized exact scorer, game-law budget, gem-floor ladder, pool-aware corridor -- and the measured per-row wall

Production-bench truth (LOVERS' OASIS Easy, production spec defaults, n=20
seed=1): **all 20 queries CAP at max_rows=5M in the decomposition join,
25-67s each, zero answers.** The earlier "min 3.65 / p50 11.5 / max 32s"
numbers were a CONSTRAINED domain; at real production caps the engine
answered nothing. Changes shipped this session, in causal order:

1. **Vectorized canonical batch scorer** (owning layer:
   `exact_rescore.score_stats_exact_batch` + new array-native
   `score_stat_arrays_exact_batch`). The exact score factors through
   (2*primary + secondary, PP/CM/FM curve VALUES, FT cell, FF cell): rows
   collapse on that derived key, then each (FT, FF) frontier cell is
   replayed once, vectorized over rows x pool lanes (exact-integer f64
   reductions, guarded < 2^52, int64 accumulation; per-element f64 op order
   identical to the per-row path). Parity: 4,015 adversarial rows
   bit-identical (plateau boundaries, clamps, zero rows, color-heavy);
   guardian test `tests/test_score_stats_exact_batch_vectorized.py`.
   Throughput ~0.8M rows/s vs ~25k/s for the old per-row loop (~32x), more
   under plateau-heavy engine batches. The old loop, the oracle's pickled
   process pool, and the --workers CLI plumbing are DELETED (canonical
   route rule); `oracle.score_stats_matrix` is the engine's array entry.
2. **Game-law upgrade budget**: production/meta specs declared
   `upgrade_total_max = per_type_cap * 6` (540) -- but 6 pieces x 15 slots
   = 90 is the hard game law, and witness assembly already rejected
   anything above it. The join was carrying ~6x physically unassemblable
   upgrade mass. Fixed at the spec layer AND clamped in `invert()`
   (`upgrade_budget = min(spec, 6 * UPGRADES_PER_PIECE_MAX)`).
3. **S-corridor pruning in the walk** (`s_corridor_keep`), both walls
   carrying explicit soundness proofs, now POOL-AWARE: per-song
   (FT, FF)-cell body-fever ranges (`oracle.fever_body_range_grids`) bound
   every completion's fever-hit count over the branch's reachable cell
   rectangle -- this closes most of the all-fever/all-normal spread that
   made the removed v1 bound useless. The v1 unsoundness root cause is
   fixed and documented in place: the elemental gem maximum OVERWROTE the
   on-color +3 side-effect mass (max instead of +=). Gem maxima are
   exact-P-conditioned (`gem_hi_r[r]`), gem minima (floors) feed the lower
   wall.
4. **Gem-floor ladder** (`DomainSpec.gem_min_per_type` +
   `invert_progressive`): gems dominate real rows' P, so the analytic-gem
   slack (= the P band width the join must survive) collapses from
   thousands to ~the elemental spread when gems are pinned near cap.
   Floors thread the analytic machinery exactly (mandatory mass in
   `p_reachable`/`min_p`, band high side in `_build_composites`, coin
   minima through `_gem_expand` and witness reconstruction -- floors
   constrain TOTAL units, visible k + invisible slack). `CapExceeded` is
   split out of `EngineError` so the ladder can abort on capacity
   specifically (wider rungs are supersets). `invert-row` and
   `identify_player` seeds run the ladder; sub-domain hits are reported
   with the explicit "complete WITHIN gems>=F/type" caveat and cross-row
   confirmation is the certainty mechanism. The multirow gate caught the
   protocol's completeness edge on its first full run: a spurious
   sub-domain seed class eliminated by another row must ESCALATE the seed
   to the full spec and re-filter (implemented in identify_player;
   full-domain elimination = genuine cross-row inconsistency, loud).

**Measured wall that survives all of it**: Gateway top-1 (P=5834,
S=19,879,361, single-color) at rung 0 (meta minis, gems pinned at cap 20;
gem band [1660, 1948], width 288) still has **>150M corridor-surviving
exact-P non-gem leaf states** (composites [4, 4x4096, 14691, 47616,
71836]). The player's non-gem P (~3886..4174) sits mid-band of the non-gem
domain; at top-1 scores the corridor cannot separate candidates because
EVERYTHING in the pinned sub-domain plausibly reaches S -- only the exact
discrete S equation discriminates. Conclusion, consistent with the
adversarial review: single-row, full-width, sub-10s inversion of this
regime is not reachable by walk pruning. The identification product runs
through multi-row intersection with ladder seeds; the engine-side unlock
is the architecture below.

### 2026-07-17 (session 3): honest caps, level-synchronous walk, exact-S key targeting -- and the wall pinned to the upgrade cross

Push round following the user's directive (branch published as
feat/reverse-score-engine). Shipped:

1. **Level-synchronous decomposition walk.** The depth-first walk
   re-expanded each (composite, remaining-P) node once per arrival path;
   identical states multiplied through the remaining slices, so the old
   row caps fired on PATH MULTIPLICITY, not real volume (a tiny CLI-small
   query could blow the 5M "result" cap on raw appends). The walk is now
   level-synchronous: all partial-state sets arriving at one (i, r) node
   merge and dedup BEFORE the node expands (clamp folding is
   path-independent within a case, so per-node dedup is exact), pending
   arrivals consolidate incrementally, levels live in int32, and max_rows
   caps DISTINCT rows per level. Peak RAM stays a small multiple of the
   cap (a first uncapped draft hit 16.6 GB on the no-pagefile box and was
   killed; the bounded version holds ~1.4 GB at a 40M cap).
2. **Exact-S key targeting** (`_SKeyMemo`, `score_derived_batch`): for a
   fixed (FT/FF cell, CM, FM, PP plateau) the exact score is
   non-decreasing in base_int, so the S-preimage is ONE integer interval,
   bisected through the canonical batch scorer (~23 vectorized rounds).
   EAGER mode (small global windows) enumerates every combo up front and
   proves domain-wide NO PREIMAGE when empty; LAZY mode bisects
   per-branch boxes on demand with a per-combo memo. Branch kill: no key
   intersects the branch's derived-envelope box => no completion can
   score exactly S.
3. **Below/above-ceiling naked-fingerprint classification** (user
   diagnosis): the exact -800 rows are coupled press-timing plays scored
   on the NAKED fever bar -- below-ceiling mismatches now name that
   cause; above-ceiling stays wrong-chart/version-drift.

**Single-query yardstick** (production spec, ladder, 5M cap):
- Gateway top-1: 22.2s FAIL (false raw-append cap) -> 48.8s FAIL (honest:
  >5M DISTINCT rows at a mid level). Stacked synthetic P=5032: 13.8s ->
  51.5s FAIL (same). Small-spec single inversion: 55.3s ok (the new
  per-branch machinery costs ~2x on tiny domains -- overhead, not
  volume).
- Volume probes with the honest walk: Gateway rung-0 (gems pinned, band
  288) exceeds 40M distinct states at LEVEL 4 -- buff x three upgrade
  subgroups alone, before minis or gear ever join. Reversing the join
  order (gear first) is no better: gear x gear is a multi-billion-row raw
  cross at level 1. No composite ordering fixes this.

**Sharpened verdict**: the mixer is the UPGRADE COUNT LATTICE. Upgrade
types are coin types (count x fixed stat pattern, per-type cap 90, joint
budget 90) -- structurally identical to gems, which the engine already
handles analytically. The v3 architecture below therefore applies the
count-vector treatment to upgrades AND gems: fold only gear x minis x
buff as materialized states (mixing-poor tables), and hash-join
upgrade/gem count-vectors on exact P with inline exact-S retention.

### Designed next architecture (evidence-backed, not yet built)

1. **S-preimage key targeting**: enumerate the exact-S derived-key set
   FIRST (per achievable (FT, FF) cell x CM x FM plateau values, the score
   is monotone in base_value -> the S-preimage is one base interval,
   bisectable with exact batch evals); then the walk kills any branch
   whose [lo, hi] stat envelope cannot reach ANY hit key. The walk stops
   discovering S and starts targeting a ~1e2-1e4-key set.
2. **Count-vector gem join**: explicit gem count vectors (k1..k5, f)
   hash-joined with leaves on exact P (a vector's P is count-determined --
   P is raw -- so the entire slack/coins machinery disappears); saturation
   is vectorized clamp math; ladder floors keep the vector set small.
3. **Streaming leaves**: bounded chunks flow through gem join -> derived
   keys -> cell-batch scoring; only exact-S survivors are retained.
   max_rows then guards retained hits, not intermediate volume.
4. **Two-color collapse**: every observable sees a two-color song's
   (c1, c2) only through v = 2*c1 + c2 (P = 2v, score base = v, N
   stat-free), so the two color axes merge losslessly into one -- a large
   state-space cut on two-color charts and a cheaper witness DFS.

## v1 limitations / next steps

- Accuracy == 1 rows only; non-FC needs the judgment-sequence DP against N.
- Derived-key dedup (PP floor plateaus) before scoring — biggest cheap win.
- `DomainSpec` caps are explicit; full-live-domain profiles need the
  gem-slack analytic step (never enumerate gem allocations) before they are
  practical at mid-range P.
- Live-parity step-0 (known own-account loadout → forward-computed S/N/P
  must equal the live row byte-exactly) remains the decisive domain check;
  synthetic round-trips validate the machinery, not the tables.
- Mini song-target identity is `"<Song Name> by <Artist>"` from Minis.csv;
  oracle and engine share one implementation, so round-trips are unaffected
  even if the live identity string differs — verify at live-parity time.
